## 1. 목적

이 계획은 제품·디지털 트윈 팀이 설계 자산의 검색, 등록, 메타데이터 관리, 버전 확인과 관계 추적에서 실제로 겪는 문제를 검증한다.

Phase 1에서는 기능 선호를 묻기 전에 현재 업무, 비용, 오류와 우회 방법을 관찰한다. 결과는 문제 가설의 유지, 수정 또는 폐기와 MVP Scope v1 승인에 사용한다.

## 3. 연구 질문

1. 사용자는 어떤 상황에서 최신 자산과 관련 근거를 찾아야 하는가.
2. 한 자산을 등록하고 승인하는 현재 Workflow는 어떻게 구성되는가.
3. 자산, 버전, 메타데이터와 관계 중 어떤 정보가 가장 자주 누락되거나 충돌하는가.
4. 오류와 재작업은 어디에서 발생하고 어떤 비용을 만든다.
5. AI가 제안해도 되는 필드와 사람이 반드시 승인해야 하는 필드는 무엇인가.
6. 사용자는 AI 결과의 출처, 권한과 최신성을 어떻게 판단하는가.
7. Digital Twin과 Knowledge Graph 개념이 현재 업무 언어와 맞는가.
8. 파일럿에서 사용할 수 있는 데이터와 보안 제약은 무엇인가.

## 4. 참여자 기준

### 목표 표본

- 총 6–8명을 권장한다.
- Enterprise Product Engineer 또는 유사 역할을 3명 이상 포함한다.
- Digital Twin Engineer 또는 유사 역할을 3명 이상 포함한다.
- 동일 조직에 편중되지 않도록 가능하면 2개 이상 조직에서 모집한다.
- 최소 5명의 유효 세션을 Phase 1 Exit Gate의 하한으로 사용한다.

### 포함 기준

- 제품, 부품, 설계 또는 Digital Twin 자산을 업무에서 직접 다룬다.
- 최근 3개월 안에 자산 검색, 등록, 검토, 승인 또는 전달 업무를 수행했다.
- 현재 사용하는 저장소, PLM, DAM, CAD 관리 또는 문서 도구를 설명할 수 있다.
- 실제 사례를 익명화해 설명하거나 합법적인 샘플로 과업을 수행할 수 있다.

### 제외 기준

- 실제 Workflow 경험 없이 구매 또는 영업 의사결정만 담당한다.
- 데이터 사용 권리를 확인할 수 없는 고객 파일만 제시할 수 있다.
- K-Legonara 구현 팀의 설계 의도를 그대로 반복해 독립적인 근거가 되기 어려운 참여자다.

## 5. 방법과 순서

| 순서 | 방법 | 시간 | 산출물 |
|---:|---|---:|---|
| 1 | 이해관계자 정렬 인터뷰 | 30분 | 목표, 제약과 모집 기준 |
| 2 | 문제 인터뷰 | 45–60분 | 최근 사례, 현재 대안과 비용 |
| 3 | Contextual Workflow Walkthrough | 45분 | 단계, 도구, Handoff와 오류 |
| 4 | Concept Task | 30분 | Option A의 이해도, 가치와 신뢰 요구 |
| 5 | 데이터·보안 검토 | 30분 | 허용 데이터, 보존과 외부 처리 제약 |
| 6 | Synthesis Workshop | 60–90분 | 근거 지도, 결정과 후속 질문 |

기능 설명은 문제 인터뷰와 현재 Workflow 관찰이 끝난 뒤에만 제시한다.

## 6. 세션 가이드

### 최근 사례

- 최근에 최신 설계 자산이나 부품 정보를 찾아야 했던 상황을 설명해 달라고 요청한다.
- 처음부터 완료까지 사용한 도구와 사람을 순서대로 확인한다.
- 예상보다 오래 걸린 단계와 다시 작업한 부분을 확인한다.
- 잘못된 버전이나 누락된 정보가 발견된 실제 사례를 확인한다.
- 현재 방식이 충분히 잘 작동하는 부분도 확인한다.

### 자산 등록과 승인

- 새 자산이 어디에서 시작되고 누가 메타데이터를 입력하는지 확인한다.
- 필수 필드, 식별자, 버전과 승인 상태를 확인한다.
- 다른 시스템으로 전달할 때 다시 매핑하는 정보를 확인한다.
- 변경 이력과 결정 근거를 어디에 남기는지 확인한다.

### AI 신뢰

- AI가 자동으로 제안해도 되는 항목을 확인한다.
- 오류 비용이 커서 사람이 반드시 검토해야 하는 항목을 확인한다.
- 출처, 모델 정보, 신뢰 정보와 승인 이력 중 필요한 근거를 확인한다.
- 권한이 없는 자료가 검색 결과에 섞일 때의 위험을 확인한다.

### Concept Task

다음 개념 흐름을 간단한 Wireframe이나 카드로 제시한다.

```text
Project
→ Asset Upload
→ AI Metadata Proposal
→ Human Review
→ Digital Twin Identity
→ Knowledge Relationships
→ Search and Grounded AI Answer
```

참여자에게 각 단계의 목적을 자신의 말로 설명하고, 불필요한 단계와 빠진 단계를 표시하도록 요청한다.

## 7. 과업 시나리오

### Task A. 최신 자산 찾기

특정 Component의 최신 승인 버전, 관련 문서와 변경 근거를 찾도록 한다.

측정 항목은 완료 여부, 소요 시간, 잘못 선택한 버전, 확인한 근거와 도움 요청이다.

### Task B. 새 자산 등록하기

허용된 Fixture를 등록하고 AI가 제안한 메타데이터를 검토해 승인 가능한 Twin Draft를 만들도록 한다.

측정 항목은 필드 이해도, 수정·거절 행동, 완료 시간, 오류와 중단 지점이다.

### Task C. 근거 있는 답 확인하기

등록한 자산과 관련된 질문을 하고 AI 응답의 Citation, 권한과 최신성을 판단하도록 한다.

측정 항목은 답의 이해도, 출처 확인 행동, 신뢰 판단과 잘못된 확신 여부다.

## 8. 기록과 데이터 보호

- 녹화, 화면 공유와 원본 파일 사용은 세션 전에 명시적으로 동의받는다.
- 고객명, 개인식별정보, 계약 정보와 영업 비밀은 연구 자료에서 제거한다.
- 원본 자산의 복사·업로드가 허용되지 않으면 화면 설명이나 합성 Fixture를 사용한다.
- 연구 노트에는 참여자 코드를 사용하고 개인 연락처를 포함하지 않는다.
- 보존 기간, 접근자와 폐기 방법은 연구 실행 전에 Product Owner와 Security Owner가 승인한다.
- 승인되지 않은 고객 데이터를 외부 AI 모델로 전송하지 않는다.

## 9. 분석 방식

각 관찰은 `사실`, `사용자 해석`, `팀 해석`, `결정 영향`으로 구분한다.

| 분류 | 예시 |
|---|---|
| 사실 | 참여자가 최신 버전을 찾기 위해 세 시스템을 확인했다 |
| 사용자 해석 | 승인 상태를 신뢰할 수 없어 담당자에게 다시 물었다 |
| 팀 해석 | 통합 검색보다 승인 Provenance가 우선일 수 있다 |
| 결정 영향 | MVP의 Twin 상태와 감사 이력 요구를 유지한다 |

가설마다 지지, 반증과 미확인 근거를 함께 기록한다. 긍정적인 발언만으로 채택하지 않는다.

## 10. 제안 판정 기준

다음 기준은 Research Owner가 실행 전에 승인하거나 수정해야 하는 Proposed Threshold다.

| 항목 | 유지 기준 | 수정 또는 중단 신호 |
|---|---|---|
| 문제 반복성 | 유효 세션 5개 중 4개 이상에서 최근 사례 확인 | 추상적 선호만 있고 최근 사례가 없음 |
| 문제 심각도 | 시간, 오류, 재작업 또는 위험 중 하나가 측정됨 | 비용이 작고 현재 대안으로 충분함 |
| Option A 적합성 | 핵심 흐름의 목적을 도움 없이 설명 | Digital Twin 단계가 실제 업무와 연결되지 않음 |
| AI Review 필요성 | 필드별 승인과 근거 요구가 반복됨 | 자동화 가치가 없거나 위험이 통제 불가능함 |
| 파일럿 가능성 | 합법적 Fixture와 담당자가 확보됨 | 데이터 권리 또는 보안 제약으로 검증 불가 |
